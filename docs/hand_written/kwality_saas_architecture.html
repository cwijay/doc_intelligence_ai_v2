1. System Overview

Kwality SaaS evolves the single-tenant DeepAgents + GCP food manufacturing platform into a scalable multi-tenant architecture. Each tenant runs on shared Cloud Run infrastructure with complete data isolation through Row-Level Security (RLS), GCS bucket prefixes, and per-tenant Gemini File Search Stores.

Multi-Tenant Model

Shared Compute, Isolated Data

Compute: All tenants run on the same Cloud Run service, scaled automatically by request volume. DeepAgents orchestrators are instantiated per tenant but share the same container image.

Data Isolation: Enforced at three layers—PostgreSQL Row-Level Security, GCS bucket prefixes, and Gemini File Search Stores (one per tenant). Tenant identity is verified via JWT and passed through all service calls.

Context Injection: Each API request includes a tenant context that flows through Next.js API routes → Cloud Run orchestrator → downstream services (Gemini, Cloud SQL, GCS, File Search).

2. Multi-Tenancy Data Isolation

Data isolation is enforced through three complementary layers. No single point of failure exposes cross-tenant data.

Three Isolation Layers

Layer 1: Cloud SQL RLS

Mechanism: PostgreSQL Row-Level Security policies on every table.

How: Each row contains a tenant_id column. Before every query, the connection middleware sets the current tenant via SET app.current_tenant. RLS policies then filter rows automatically.

Benefit: Database-level enforcement. A bug in application code cannot leak cross-tenant data.

Layer 2: GCS Bucket Prefixes

Mechanism: Tenant-namespaced folder structure.

Path: gs://kwality-saas/{tenant_id}/orders/, gs://kwality-saas/{tenant_id}/output/

Benefit: Object-level isolation. IAM permissions and access logs are tenant-aware.

Layer 3: Gemini File Search

Mechanism: One File Search Store per tenant.

Storage: Store name (UUID) is persisted in the tenants table during onboarding.

Benefit: RAG retrieval is tenant-scoped by default. Agents query only their own document store.

Cloud SQL RLS Setup

The following SQL initializes RLS on the orders table (pattern applies to all tables):

-- Create orders table with tenant_id
CREATE TABLE orders (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    order_number VARCHAR(255) NOT NULL,
    created_at TIMESTAMP DEFAULT now(),
    FOREIGN KEY (tenant_id) REFERENCES tenants(id) ON DELETE CASCADE
);

-- Enable RLS
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

-- Create policy: users see only their tenant's rows
CREATE POLICY tenant_isolation ON orders
    USING (tenant_id = current_setting('app.current_tenant')::uuid);

-- Optionally, restrict INSERT/UPDATE to current tenant
ALTER TABLE orders FORCE ROW LEVEL SECURITY;

Tenant Context Middleware (Next.js API)

This middleware extracts the tenant from the JWT and passes it to the Cloud Run backend:

// middleware/tenantContext.ts
import { verifyJWT } from './jwt';
import { NextRequest, NextResponse } from 'next/server';

export async function tenantContextMiddleware(
  request: NextRequest
) {
  const token = request.headers.get('Authorization')?.replace('Bearer ', '');
  if (!token) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });

  const payload = await verifyJWT(token);
  const tenantId = payload.tenant_id;

  // Clone request and add tenant context
  const requestHeaders = new Headers(request.headers);
  requestHeaders.set('X-Tenant-ID', tenantId);

  return request.clone({ headers: requestHeaders });
}

// pages/api/orders.ts
export default async function handler(
  request: NextApiRequest,
  response: NextApiResponse
) {
  const tenantId = request.headers['x-tenant-id'];

  // Forward to Cloud Run with tenant context
  const cloudRunResponse = await fetch(
    `${process.env.CLOUD_RUN_URL}/orchestrate`,
    {
      method: 'POST',
      headers: { 'X-Tenant-ID': tenantId },
      body: JSON.stringify({ action: 'fetch_orders' })
    }
  );

  return response.json(await cloudRunResponse.json());
}

Cloud Run Tenant Context Handler (Python)

The DeepAgents runtime on Cloud Run receives the tenant context and applies it to database connections:

# cloud_run/orchestrator.py
from fastapi import FastAPI, Header
from sqlalchemy import create_engine, event, text

app = FastAPI()
engine = create_engine(DATABASE_URL)

@app.post("/orchestrate")
async def orchestrate(
    tenant_id: str = Header(None, alias="x-tenant-id")
):
    # Set RLS context for this connection
    with engine.connect() as conn:
        conn.execute(
            text(f"SET app.current_tenant = '{tenant_id}'")
        )
        # All subsequent queries are automatically filtered by RLS
        orders = conn.execute(
            text("SELECT * FROM orders")
        ).fetchall()

    return { "orders": orders }

3. Gemini File Search Store as RAG

Each tenant has a dedicated Gemini File Search Store. During onboarding, the platform creates a store and persists its name in the tenants table. Agents query this store to retrieve grounded, tenant-specific documents (SOPs, HACCP templates, batch sheets, quality standards).

RAG Architecture

Per-Tenant Knowledge Base

Data Flow: Tenant uploads documents → File Search Store (indexed, chunked, embedded) → Agent query → Gemini retrieves relevant chunks → Grounded response with citations.

Isolation: Each tenant's documents live in their own store. No cross-tenant leakage.

Scalability: Gemini File Search handles large document sets (SOPs, regulatory docs, batch archives).

async def onboard_tenant(company_name: str, tenant_id: str):

    client = genai.Client(
        vertexai=True,
        project="kwality-saas",
        location="us-central1"
    )

    # Create File Search Store for this tenant

    )

    # Store the File Search Store name in the database
    await db.execute(

Upload Tenant Document

When a tenant uploads a SOP or other document, add it to their File Search Store:

@app.post("/documents/upload")
async def upload_document(
    file: UploadFile,
    tenant_id: str = Header(None, alias="x-tenant-id")
):
    # Get tenant's File Search Store name from DB
    tenant = await db.fetch_one(
        "SELECT file_search_store_name FROM tenants WHERE id = %s",
        [tenant_id]
    )

    # Upload to File Search Store
    client = genai.Client(vertexai=True, project="kwality-saas")

    operation = client.file_search_stores.upload_to_file_search_store(
        file=await file.read(),
        file_search_store_name=tenant.file_search_store_name,
        config={
            'display_name': file.filename
        }
    )

    # Wait for indexing
    result = operation.result()

    return { "file_id": result.file_id, "status": "indexed" }

Agent Queries Tenant's Store

When an agent needs to answer a question, it queries the File Search Store. The store is passed as a tool to the orchestrator:

# Agent querying grounded on tenant's File Search Store
from google.genai import types

async def query_with_rag(
    question: str,
    tenant_id: str
):
    # Get tenant's File Search Store name
    tenant = await db.fetch_one(
        "SELECT file_search_store_name FROM tenants WHERE id = %s",
        [tenant_id]
    )

    client = genai.Client(vertexai=True, project="kwality-saas")

    # Create File Search tool scoped to this tenant's store
    file_search_tool = types.Tool(
        file_search=types.FileSearch(
            file_search_store_names=[tenant.file_search_store_name]
        )
    )

    # Generate response grounded in tenant's documents
    response = client.models.generate_content(
        model="gemini-3-flash",
        contents=question,
        config=types.GenerateContentConfig(
            tools=[file_search_tool],
            temperature=0.5
        )
    )

    return {
        "answer": response.text,
        "sources": extract_citations(response)
    }

4. Agent Architecture (Multi-Tenant)

The DeepAgents runtime is extended to support multi-tenant operation. Orchestrators are created per-tenant with injected context. A new Tenant Provisioning Agent handles onboarding automation.

Tenant-Aware Orchestrator

Each tenant gets its own orchestrator instance with tenant-scoped tools and prompts:

# orchestrators/tenant_orchestrator.py
from langchain.agents import AgentExecutor, create_react_agent
from langchain_google_vertexai import ChatGoogleGenerativeAI
from langgraph.checkpoint.postgres import PostgresSaver
import google.genai as genai

async def create_tenant_orchestrator(tenant_id: str) -> AgentExecutor:
    # Fetch tenant from database
    tenant = await db.fetch_one(
        "SELECT * FROM tenants WHERE id = %s",
        [tenant_id]
    )

    # Initialize LLM with Gemini 3 Flash
    llm = ChatGoogleGenerativeAI(
        model="gemini-3-flash",
        temperature=0.3,
        google_api_key=GOOGLE_API_KEY
    )

    # Create tenant-scoped File Search tool
    client = genai.Client(vertexai=True)
    file_search_tool = types.Tool(
        file_search=types.FileSearch(
            file_search_store_names=[tenant.file_search_store_name]
        )
    )

    # Define tenant-specific tools
    tools = [
        make_reconcile_tool(tenant_id),
        make_notify_staff_tool(tenant_id),
        make_ocr_tool(tenant_id),
        make_gcs_upload_tool(tenant_id),
        file_search_tool  # RAG tool
    ]

    # System prompt includes tenant name
    system_prompt = f"""
You are the orchestrator for {tenant.company_name} food manufacturing operations.
Your role is to:
1. Process incoming orders and extract data via OCR
2. Reconcile with internal ERP system
3. Recommend quality checks based on production standards
4. Answer questions about SOPs, HACCP, and batch procedures

Tenant-specific context:
- Company: {tenant.company_name}
- Max daily orders: {tenant.max_orders_per_day}
- QC standards: {tenant.qc_standard}
- Contact: {tenant.support_email}

When users ask about procedures, always ground answers in the tenant's File Search Store.
"""

    # Create agent with state persistence (checkpoint)
    agent = create_react_agent(
        llm=llm,
        tools=tools,
        prompt=system_prompt

    # Add checkpoint for state persistence
    checkpointer = PostgresSaver.from_conn_string(DB_URL)

    executor = AgentExecutor(
        agent=agent,
        tools=tools,

        handle_parsing_errors=True

    return executor

async def provision_tenant(

6. API Layer (Next.js → Cloud Run)

The API layer is a Bridge pattern: Next.js API routes act as a Backend for Frontend (BFF), validating JWT tokens, extracting tenant context, and forwarding requests to Cloud Run. This design isolates frontend clients from backend orchestration and enables tenant-scoped request handling.

API Architecture

Three-Tier Request Flow

Tier 1 (Client): React frontend sends authenticated requests with JWT in Authorization header.

Tier 2 (Next.js BFF): API routes validate JWT, extract tenant_id, inject X-Tenant-ID header, and forward to Cloud Run.

Tier 3 (Cloud Run): Orchestrator receives tenant context, applies it to database/GCS/File Search calls.

Next.js API Route: Order Ingest

This endpoint receives order images, uploads them to tenant-scoped GCS, and triggers the Cloud Run agent:

// app/api/orders/ingest/route.ts
import { NextRequest, NextResponse } from 'next/server';
import { validateJWT } from '@/lib/jwt';
import { uploadToGCS } from '@/lib/gcs';

const CLOUD_RUN_URL = 'https://kwality-backend.run.app';

export async function POST(req: NextRequest) {
  try {
    // Validate JWT and extract tenant
    const token = req.headers.get('Authorization')?.replace('Bearer ', '');
    if (!token) return NextResponse.json(
      { error: 'Unauthorized' },
      { status: 401 }
    );

    const payload = await validateJWT(token);
    const tenantId = payload.tenant_id;

    // Parse multipart form data
    const formData = await req.formData();
    const file = formData.get('orderPhoto') as File;

    if (!file) {
      return NextResponse.json(
        { error: 'No file provided' },
        { status: 400 }
      );
    }

    // Upload to tenant-scoped GCS folder
    const buffer = await file.arrayBuffer();
    const gcsUri = await uploadToGCS(
      tenantId,
      file.name,
      Buffer.from(buffer)
    );

    // Get service token for Cloud Run authentication
    const serviceToken = await getServiceToken();

    // Trigger Cloud Run orchestrator with tenant context
    const cloudRunResponse = await fetch(
      `${CLOUD_RUN_URL}/orders/process`,
      {
        method: 'POST',
        headers: {
          'X-Tenant-ID': tenantId,
          'Authorization': `Bearer ${serviceToken}`,
          'Content-Type': 'application/json'
        },
        body: JSON.stringify({
          type: 'order_photo',
          gcs_uri: gcsUri,
          filename: file.name
        })
      }
    );

    const result = await cloudRunResponse.json();

    return NextResponse.json({
      success: true,
      gcs_uri: gcsUri,
      orchestration_id: result.id
    });
  } catch (err) {
    return NextResponse.json(
      { error: err.message },
      { status: 500 }
    );
  }
}

SSE Endpoint: Agent Activity Stream

Real-time server-sent events for agent activity, sensor data, and alerts. Clients subscribe and receive live updates filtered to their tenant:

// app/api/agents/stream/route.ts
import { NextRequest } from 'next/server';
import { validateJWT } from '@/lib/jwt';
import { PubSub } from '@google-cloud/pubsub';

export async function GET(req: NextRequest) {
  // Validate tenant
  const token = req.headers.get('Authorization')?.replace('Bearer ', '');
  const payload = await validateJWT(token);
  const tenantId = payload.tenant_id;

  // Create SSE stream
  const encoder = new TextEncoder();
  const pubsub = new PubSub({
    projectId: 'kwality-saas'
  });

  const stream = new ReadableStream({
    async start(controller) {
      // Subscribe to tenant-specific topic
      const sub = pubsub.subscription(
        `agent-events-${tenantId}`
      );

      // Forward messages to client
      sub.on('message', msg => {
        controller.enqueue(
          encoder.encode(
            `data: ${msg.data.toString()}\n\n`
          )
        );
        msg.ack();
      });

      sub.on('error', err => {
        controller.error(err);
      });

      // Keep connection alive
      const keepAlive = setInterval(() => {
        controller.enqueue(
          encoder.encode(`: heartbeat\n\n`)
        );
      }, 30000);

      return () => clearInterval(keepAlive);
    }
  });

  return new Response(stream, {
    headers: {
      'Content-Type': 'text/event-stream',
      'Cache-Control': 'no-cache',
      'Connection': 'keep-alive'
    }
  });
}

Provisioning Agent: Key Orchestration

# Triggered when user confirms tenant creation
async def provision_tenant(
    company_name: str,
    admin_email: str,
    products: List[Dict],
    sop_gcs_uris: List[str]
) -> Dict:
    # 1. Generate unique tenant ID
    tenant_id = str(uuid.uuid4())

    # 2. Create File Search Store
    client = genai.Client(vertexai=True)
    store = client.file_search_stores.create(
        config={'display_name': f'{company_name}-docs'}
    )

    # 3. Create tenant in database
    await db.execute(
        "INSERT INTO tenants (...) VALUES (...)",
        [tenant_id, company_name, admin_email, store.name, 'active']
    )

    # 4. Create GCS tenant folders
    gcs = storage.Client()
    bucket = gcs.bucket("kwality-saas")
    for prefix in ['orders', 'output', 'docs']:
        bucket.blob(f"{tenant_id}/{prefix}/.keep").upload_from_string("")

    # 5. Index uploaded SOPs in File Search Store
    for gcs_uri in sop_gcs_uris:
        client.file_search_stores.upload_to_file_search_store(
            file_uri=gcs_uri,
            file_search_store_name=store.name
        )

    # 6. Seed product catalog
    for product in products:
        await db.execute(
            "INSERT INTO products (tenant_id, name, sku, category) VALUES (%s, %s, %s, %s)",
            [tenant_id, product['name'], product['sku'], product.get('category', 'other')]
        )

    # 7. Send welcome email
    await send_welcome_email(admin_email, company_name)

    return {"tenant_id": tenant_id, "status": "provisioned"}

9. Security Model

Kwality SaaS implements a three-layer security model: authentication (NextAuth + JWT), API-level tenant verification, and data-layer isolation (RLS, GCS IAM, File Search Store per-tenant).

Three Security Layers

Layer 1: Authentication (NextAuth.js)

Provider: Google OAuth 2.0 (federated identity). Users sign in with their Google account.

JWT Token: Upon successful login, NextAuth issues a JWT containing tenant_id, user_id, and role (admin/editor/viewer).

Token Usage: All client requests include Authorization: Bearer {JWT} header. The token is verified server-side before any data access.

Layer 2: API & Request Validation

Middleware: Every Next.js API route runs tenant context middleware that validates the JWT and extracts the tenant_id.

Header Injection: The tenant_id is injected as X-Tenant-ID header and forwarded to Cloud Run. No cross-tenant requests are allowed.

Verification: Cloud Run validates the service-to-service token and ensures the tenant context matches the requestor.

Layer 3: Data Isolation (RLS, GCS, File Search)

PostgreSQL RLS: Every query is automatically filtered by tenant_id via Row-Level Security policies. A query returning "all orders" actually returns only orders for the current tenant.

GCS IAM Conditions: Service accounts have conditional access to the GCS bucket. A Cloud Run instance serving Tenant A cannot read objects from Tenant B's prefix.

File Search Store: Each tenant's documents live in a separate Gemini File Search Store. The orchestrator only queries the tenant's store via the API.

Security Verification Checklist

Layer Mechanism Verification Method
Auth NextAuth.js + Google OAuth Check Authorization header; verify JWT signature; decode tenant_id from claims

Defense-in-Depth Example

Scenario: A malicious user from Tenant A tries to access Tenant B's data.

Attack Attempt & Defense
  1. Layer 1 Defense: User tries to modify their JWT to claim tenant_id = B. NextAuth validates signature; JWT is rejected. Request fails.
  2. Layer 2 Defense: User creates a valid JWT but sends X-Tenant-ID: tenant-b header directly. Middleware compares header to JWT claims; mismatch is detected. Request rejected.
  3. Layer 3 Defense: Assuming somehow the API request reaches Cloud Run, the SQL query SELECT * FROM orders WHERE tenant_id = 'A' is executed. PostgreSQL RLS policy intercepts and filters: WHERE tenant_id = 'A' AND tenant_id = (current_setting) = false. No rows returned.
  4. Logging: All three rejections are logged; security alert triggered for repeat attempts.

Metering Architecture: Cloud Run → BigQuery

Automated Usage Tracking

Step 1: All Cloud Run orchestrator requests log usage events: order count, OCR calls, API requests, token consumption (via Vertex AI API logs).

Step 2: Cloud Logging exports to BigQuery daily. Each log entry tagged with tenant_id and event type.

Step 3: BigQuery queries compute monthly usage per tenant. Results feed billing system.

Step 4: Billing dashboard shows real-time usage, projected month-end charges, and overage warnings.

Billing Example

-- BigQuery query: Compute monthly usage for Tenant A
SELECT
  tenant_id,
  COUNT(DISTINCT order_id) AS orders,
  COUNT(CASE WHEN event_type = 'ocr_call' THEN 1 END) AS ocr_count,
  SUM(gcs_bytes_written) / POWER(10, 9) AS storage_gb,
  SUM(gemini_tokens_used) AS total_tokens
FROM kwality_usage_logs
WHERE
  tenant_id = 'tenant-uuid'
  AND DATE(event_timestamp) BETWEEN '2024-01-01' AND '2024-01-31'
GROUP BY tenant_id;
