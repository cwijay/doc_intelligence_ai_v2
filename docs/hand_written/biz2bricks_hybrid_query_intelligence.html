1. The Hybrid Query Problem

The Biz2Bricks platform extracts structured data and indexes raw documents, but users need a single natural language interface to ask questions that span both. This section explains why neither text-to-SQL nor RAG alone is sufficient.

Structured vs. Unstructured Data

Every Biz2Bricks tenant has two complementary data sources:

Structured Data (Cloud SQL)

Extracted fields from processed documents: amounts, dates, quantities, statuses, normalized values. Perfect for aggregation, filtering, comparison, and time-series analysis.

Examples: invoice totals, delivery dates, defect rates, candidate experience years

Unstructured Data (Gemini File Search)

Raw document content: paragraphs, clauses, notes, comments, inspection observations. Perfect for context, specifics, and qualitative details.

Examples: penalty clauses, temperature observations, candidate background, inspection notes

The Spectrum: SQL vs. Hybrid vs. RAG

User questions fall along a spectrum. The router classifies each into one of three routes:

SQL Only

"What's my total spend?" "Top 5 suppliers?" "Average time-to-hire?"

→

Hybrid

"Invoices over $10K that mention penalties" "Failed batches and their corrective actions"

→

RAG Only

"What did the audit say?" "Competitor terms?" "Inspection observations?"

Vertical Examples

Food Manufacturing

SQL "Total production output for March" → Sum extracted quantities

RAG "What temperature was flagged in HACCP audit?" → Search raw audit documents

HYBRID "Show me all batches that failed QC and what the corrective actions were" → Find failed records, enrich with RAG for action details

Recruitment

SQL "Average time-to-hire this quarter" → Aggregate extracted dates

RAG "Which candidate mentioned Kubernetes experience?" → Full-text search CVs

HYBRID "Find candidates with 5+ years experience whose CVs mention leadership roles" → Filter SQL by years, then RAG for leadership mentions

Retail / Distribution

SQL "Top 5 suppliers by order volume" → Aggregate extracted quantities

RAG "What are the return policy terms from Supplier X?" → Search contracts

HYBRID "Suppliers with >10% defect rate — what do their contracts say about quality guarantees?" → Identify suppliers by defect rate, then retrieve contract clauses

Real Estate

SQL "Average days on market for listings above $500K" → Aggregate extracted values

RAG "What did the inspector note about the foundation?" → Search inspection reports

HYBRID "Properties listed over 90 days with inspection issues — show the defects" → Filter by days on market, then retrieve defect details from reports

Why Hybrid Matters: Without hybrid queries, users must perform manual multi-step research: run SQL, get IDs, then search RAG for context. With hybrid routing, we intelligently combine both paths and synthesize a complete answer in one natural language request.

2. Query Router Architecture

Every user question flows through a Query Router that classifies it into one of three execution paths. The router uses Gemini 3 Flash to understand the question intent and the tenant's data model.

Router Pattern

The router accepts a natural language question and returns a structured decision including the route type, rephrased sub-questions for each path, and confidence. This design allows the execution layer to confidently dispatch to the correct handler(s).

Router Implementation

from google import genai
from google.genai import types
from pydantic import BaseModel
from enum import Enum

class QueryRoute(str, Enum):
    SQL_ONLY = "sql_only"
    RAG_ONLY = "rag_only"
    HYBRID = "hybrid"

class RouterDecision(BaseModel):
    route: QueryRoute
    reasoning: str
    sql_question: str | None = None
    rag_question: str | None = None
    confidence: float

client = genai.Client(vertexai=True, project="biz2bricks-prod", location="us-central1")

ROUTER_PROMPT = """You are a query router for a document intelligence platform.

Given a user's natural language question, decide which data source(s) to query:

**sql_only** — Use when the question asks for:
- Aggregations (totals, counts, averages, min/max)
- Filtering by specific field values (dates, amounts, status)
- Sorting, ranking, or top-N queries
- Comparisons between entities or time periods
- Any question answerable from structured extracted fields

**rag_only** — Use when the question asks for:
- Specific content or wording from documents
- Qualitative information (descriptions, notes, terms, clauses)
- Context that wasn't extracted into structured fields
- "What does the document say about..."
- Free-text search across document content

**hybrid** — Use when the question needs BOTH:
- Structured filtering + document context
- Quantitative results enriched with qualitative details
- Questions that first filter entities, then need document-level detail

Available structured fields for this tenant:
{schema_description}

Available document types in RAG:
{rag_store_descriptions}

User question: {question}

Return your decision as JSON with route, reasoning, sql_question, rag_question, and confidence (0-1)."""

@app.post("/route")
async def route_query(tenant_id: str, question: str) -> RouterDecision:
    schema_desc = await get_tenant_schema_description(tenant_id)
    rag_desc = await get_tenant_rag_description(tenant_id)

    response = await client.aio.models.generate_content(
        model="gemini-3-flash",
        contents=ROUTER_PROMPT.format(
            schema_description=schema_desc,
            rag_store_descriptions=rag_desc,
            question=question,
        ),
        config=types.GenerateContentConfig(
            response_mime_type="application/json",
            response_json_schema=RouterDecision.model_json_schema(),
        ),
    )

    return RouterDecision.model_validate_json(response.text)
Implementation Note: The router uses Gemini's structured output mode (response_json_schema) to ensure consistent, parseable responses. The prompt explicitly defines the three routes and provides schema context so Gemini can make informed decisions. This pattern is resilient and requires no custom parsing.

3. Text-to-SQL Engine

The SQL path converts natural language questions into safe, executable PostgreSQL queries. The core challenge: each tenant's schema is dynamic, with base fields and custom JSONB columns that vary per tenant. The engine must understand this at generation time.

The Dynamic Schema Challenge

Unlike traditional databases with fixed schemas, Biz2Bricks extracts structured data into JSONB columns. A recruitment tenant might have custom fields like candidate_certifications or visa_sponsorship_needed, while a food manufacturer has allergen_info and batch_size. The SQL generator must be aware of all available fields at generation time.

Schema Registry

The Schema Registry builds a natural-language description of each tenant's data model. This description is embedded in the SQL generation prompt, allowing Gemini to generate queries using the correct field names and types. 

async def get_tenant_schema_description(tenant_id: str) -> str:
    """Build natural language schema description for SQL generator."""

    doc_types = await db.fetch_all("""
        SELECT dt.type_key, dt.display_name, dt.base_schema,
               json_agg(json_build_object(
                   'name', cf.field_name,
                   'type', cf.field_type,
                   'hint', cf.extraction_hint
               )) FILTER (WHERE cf.id IS NOT NULL) AS custom_fields
        FROM document_types dt
        LEFT JOIN custom_fields cf ON cf.document_type_id = dt.id
        WHERE dt.tenant_id = :tenant_id
        GROUP BY dt.id
    """, {"tenant_id": tenant_id})

    lines = ["## Database Schema", ""]
    lines.append("### Core Tables")
    lines.append("- `documents` (id, tenant_id, document_type_id, gcs_path, status, created_at)")
    lines.append("- `extracted_data` (id, document_id, tenant_id, data JSONB, validation_errors, extracted_at)")
    lines.append("")

    for dt in doc_types:
        lines.append(f"### Document Type: {dt['display_name']} (type_key='{dt['type_key']}')")

        schema = dt['base_schema']
        if 'properties' in schema:
            lines.append("Base fields in `extracted_data.data`:")
            for field_name, field_def in schema['properties'].items():
                field_type = field_def.get('type', 'string')
                lines.append(f"  - `data->>'{field_name}'` ({field_type})")

                if field_type == 'array' and 'items' in field_def:
                    item_props = field_def['items'].get('properties', {})
                    for sub_name, sub_def in item_props.items():
                        lines.append(f"    - `elem->>'{sub_name}'` ({sub_def.get('type', 'string')})")

        if dt['custom_fields']:
            lines.append("Custom fields (tenant-added):")
            for cf in dt['custom_fields']:
                hint = cf['hint'] or 'no hint'
                lines.append(f"  - `data->>'{cf['name']}'` ({cf['type']}) — {hint}")

        lines.append("")

    return "\n".join(lines)

SQL Generation with Gemini

SQL_GENERATION_PROMPT = """You are a PostgreSQL expert. Generate a query to answer:

CRITICAL RULES:
1. ALWAYS include WHERE tenant_id = :tenant_id (multi-tenant system)
2. For JSONB: use data->>'field_name' for text, (data->>'field_name')::numeric for numbers
3. For JSONB arrays: use jsonb_array_elements(data->'array_field') AS elem
4. NEVER use DELETE, UPDATE, INSERT, DROP, ALTER, or DDL/DML — only SELECT
5. ALWAYS limit to 100 rows unless aggregating
6. Use CTEs for readability
7. Cast JSONB values to proper types
8. For dates: (data->>'date_field')::date

{schema_description}

Question: {question}

Return only the SQL query, no explanation."""

async def generate_sql(tenant_id: str, question: str, schema_desc: str) -> str:
    response = await client.aio.models.generate_content(
        model="gemini-3-flash",
        contents=SQL_GENERATION_PROMPT.format(
            schema_description=schema_desc,
            question=question,
        ),
        config=types.GenerateContentConfig(
            thinking_config=types.ThinkingConfig(thinking_level="medium"),
        ),
    )

    sql = response.text.strip()
    if sql.startswith("```"):
        sql = sql.split("\n", 1)[1].rsplit("```", 1)[0].strip()

    return sql

SQL Validation & Sanitization

Before any SQL executes, it is validated and sanitized using sqlglot. This prevents injection attacks and ensures only safe SELECT statements run. 

import sqlglot

class SQLValidationError(Exception):
    pass

def validate_sql(sql: str, tenant_id: str) -> str:
    """Validate and sanitize generated SQL before execution."""

    # 1. Parse with sqlglot to ensure valid SQL
    try:
        parsed = sqlglot.parse_one(sql, dialect="postgres")
    except sqlglot.errors.ParseError as e:
        raise SQLValidationError(f"Invalid SQL syntax: {e}")

    # 2. Reject any non-SELECT statements
    if not isinstance(parsed, sqlglot.exp.Select):
        raise SQLValidationError("Only SELECT statements are allowed")

    # 3. Check for dangerous operations
    dangerous_ops = (
        sqlglot.exp.Delete, sqlglot.exp.Update, sqlglot.exp.Insert,
        sqlglot.exp.Drop, sqlglot.exp.Alter, sqlglot.exp.Create,
    )
    for node in parsed.walk():
        if isinstance(node, dangerous_ops):
            raise SQLValidationError(f"Forbidden operation: {type(node).__name__}")

    # 4. Ensure tenant_id filter exists
    sql_lower = sql.lower()
    if "tenant_id" not in sql_lower:
        raise SQLValidationError("Query must include tenant_id filter")

    # 5. Add LIMIT if not present
    if not parsed.find(sqlglot.exp.Limit):
        sql = f"SELECT * FROM ({sql}) _limited LIMIT 100"

    return sql

4. RAG Query Path

For RAG-only and hybrid queries, the router dispatches to Gemini File Search. The router rephrases the question optimally for document retrieval, and the result includes grounded citations.

Implementation

async def execute_rag_query(tenant_id: str, question: str, categories: list[str] = None) -> dict:
    """Query tenant's File Search Stores for unstructured intelligence."""
    stores = await get_tenant_stores(tenant_id)

    # Select relevant stores (router may suggest specific categories)
    store_names = [stores[c] for c in (categories or stores.keys()) if c in stores]

    response = await client.aio.models.generate_content(
        model="gemini-3-flash",
        contents=question,
        config=types.GenerateContentConfig(
            tools=[
                types.Tool(file_search=types.FileSearch(
                    file_search_store_names=store_names
                ))
            ],
            system_instruction="Answer based on tenant's documents. Always cite specific documents and quote relevant passages. If information isn't found, say so clearly.",
        ),
    )

    # Extract grounding metadata for citations
    sources = []
    if response.candidates and response.candidates[0].grounding_metadata:
        for chunk in response.candidates[0].grounding_metadata.chunks:
            sources.append({
                "file_name": chunk.file_name,
                "snippet": chunk.text,
                "relevance_score": chunk.relevance_score,
            })

    return {
        "answer": response.text,
        "sources": sources,
    }
Grounding & Citations: Gemini's File Search automatically grounds responses in the indexed documents. The grounding_metadata provides exact file names, snippets, and relevance scores. This ensures users can verify claims and trace them to source documents.

5. Hybrid Execution & Result Synthesis

For hybrid queries, both SQL and RAG paths execute in parallel. A Synthesizer then merges results into a coherent, actionable response that combines quantitative data with qualitative context.

Parallel Execution

import asyncio

async def execute_hybrid_query(
    tenant_id: str,
    question: str,
    router_decision: RouterDecision,
    schema_desc: str,
) -> dict:
    """Execute both SQL and RAG paths in parallel, then synthesize."""

    # Run both paths concurrently
    sql_task = execute_sql_path(tenant_id, router_decision.sql_question, schema_desc)
    rag_task = execute_rag_query(tenant_id, router_decision.rag_question)

    sql_result, rag_result = await asyncio.gather(sql_task, rag_task)

    # Synthesize results
    synthesis = await synthesize_results(
        question=question,
        sql_result=sql_result,
        rag_result=rag_result,
    )

    return synthesis

    }
Transparency & Trust: The response includes the generated SQL query, so users can see what data was queried. This builds trust and allows users to verify the logic. For RAG results, source documents and relevance scores are always included.

Chat API Route with SSE Streaming

// app/api/chat/route.ts
import { NextRequest } from 'next/server'

export async function POST(req: NextRequest) {
    const { message } = await req.json()
    const tenantId = req.headers.get('x-tenant-id')!

    const encoder = new TextEncoder()

    const stream = new ReadableStream({
        async start(controller) {
            // 1. Route the query
            controller.enqueue(encoder.encode(`data: ${JSON.stringify({ type: 'status', content: 'Analyzing your question...' })}\n\n`))

            const routeResponse = await invokeAgent(tenantId, 'query_intelligence', {
                action: 'route',
                question: message,
            })

            const route = routeResponse.route
            controller.enqueue(encoder.encode(`data: ${JSON.stringify({ type: 'route', content: route })}\n\n`))

            // 2. Execute query path(s)
            if (route === 'sql_only' || route === 'hybrid') {
                controller.enqueue(encoder.encode(`data: ${JSON.stringify({ type: 'status', content: 'Querying your data...' })}\n\n`))
            }
            if (route === 'rag_only' || route === 'hybrid') {
                controller.enqueue(encoder.encode(`data: ${JSON.stringify({ type: 'status', content: 'Searching your documents...' })}\n\n`))
            }

            // 3. Get full result
            const result = await invokeAgent(tenantId, 'query_intelligence', {
                action: 'execute',
                question: message,
                route: route,
            })

            // 4. Stream the response
            controller.enqueue(encoder.encode(`data: ${JSON.stringify({ type: 'answer', content: result.answer })}\n\n`))

            if (result.sql_query) {
                controller.enqueue(encoder.encode(`data: ${JSON.stringify({ type: 'sql', query: result.sql_query, rows: result.sql_data })}\n\n`))
            }

            if (result.rag_sources) {
                controller.enqueue(encoder.encode(`data: ${JSON.stringify({ type: 'sources', sources: result.rag_sources })}\n\n`))
            }

            controller.enqueue(encoder.encode('data: [DONE]\n\n'))
            controller.close()
        },
    })

    return new Response(stream, {
        headers: {
            'Content-Type': 'text/event-stream',
            'Cache-Control': 'no-cache',
            'Connection': 'keep-alive',
        },
    })
}
Progressive Display: The SSE stream allows the UI to show status updates ("Analyzing...", "Querying...") before the final answer arrives. Results are displayed progressively as each path completes, improving perceived performance.

8. SQL Safety, Guardrails & Observability

Safety is paramount. Every generated SQL is validated, executed with timeouts, and logged for analysis. A comprehensive observability pipeline tracks query health and identifies improvement opportunities.

Multi-Layer Safety

SQL Injection Prevention:
  • sqlglot parsing and validation (AST analysis)
  • Parameterized tenant_id (never string interpolation)
  • RLS (Row Level Security) as defense-in-depth
  • Only SELECT statements allowed

Query Guardrails

Guardrail Value Rationale
Execution Timeout 5 seconds Prevents runaway queries from consuming resources
Result Row Limit 100 (aggregate queries exempt) Prevents network transfer of massive datasets
Tenant Filter Required Multi-tenant isolation, prevents data leakage
Allowed Statements SELECT only No DDL/DML, read-only access

Safe Execution with Error Recovery

async def safe_execute_sql(sql: str, tenant_id: str, timeout_ms: int = 5000) -> dict:
    try:
        # Validate SQL
        validated_sql = validate_sql(sql, tenant_id)

        # Execute with timeout
        async with db.connection() as conn:
            await conn.execute("SET app.current_tenant = :tid", {"tid": tenant_id})
            await conn.execute(f"SET statement_timeout = {timeout_ms}")

            start = time.monotonic()
            rows = await conn.fetch_all(validated_sql, {"tenant_id": tenant_id})
            execution_time = time.monotonic() - start

            # Log for observability
            await log_query_execution(
                tenant_id=tenant_id,
                sql=validated_sql,
                execution_time_ms=execution_time * 1000,
                row_count=len(rows),
                status="success",
            )

            return {
                "rows": [dict(r) for r in rows],
                "sql": validated_sql,
                "execution_time_ms": execution_time * 1000
            }

    except asyncio.TimeoutError:
        await log_query_execution(tenant_id=tenant_id, sql=sql, status="timeout")
        return {"error": "Query took too long. Try a more specific question.", "sql": sql}

    except SQLValidationError as e:
        await log_query_execution(tenant_id=tenant_id, sql=sql, status="validation_error", error=str(e))
        return {"error": f"Query validation failed: {e}", "sql": sql}

    except Exception as e:
        await log_query_execution(tenant_id=tenant_id, sql=sql, status="error", error=str(e))
        return {"error": "Query execution failed. Falling back to document search.", "sql": sql}

Caching Layer

import hashlib

async def cached_sql_execute(sql: str, tenant_id: str, cache_ttl: int = 300) -> dict:
    """Cache SQL results in Redis for 5 minutes."""
    cache_key = f"sql:{tenant_id}:{hashlib.sha256(sql.encode()).hexdigest()}"

    # Check cache
    cached = await redis.get(cache_key)
    if cached:
        return json.loads(cached)

    # Execute
    result = await safe_execute_sql(sql, tenant_id)

    # Cache successful results
    if "error" not in result:
        await redis.setex(cache_key, cache_ttl, json.dumps(result, default=str))

    return result

Observability & Feedback Loop

Every query is logged with:

  • Question & Context: The original user question, tenant, timestamp
  • Routing Decision: Which route was chosen and why
  • SQL Generated: The full SQL statement (for SQL paths)
  • Execution Metrics: Time (ms), row count, success/failure
  • User Feedback: If user flags a result as incorrect

This data flows to BigQuery and powers a Query Analytics Dashboard:

  • Most-asked questions by vertical and tenant
  • Route distribution (what % of queries are hybrid?)
  • SQL generation failure rate and common patterns
  • Average execution time by question type
  • User feedback trends — where is the system wrong?
Continuous Improvement: The observability pipeline creates a feedback loop. High-failure SQL patterns inform schema updates; frequent questions inform template suggestions; user feedback drives prompt improvements.

Auto-Chart Detection

def suggest_visualization(columns: list[str], rows: list[dict]) -> dict | None:
    """Analyze SQL results and suggest appropriate visualization."""
    if not rows or len(rows) < 2:
        return None

    numeric_cols = [c for c in columns if isinstance(rows[0].get(c), (int, float))]
    text_cols = [c for c in columns if isinstance(rows[0].get(c), str)]
    date_cols = [c for c in columns if 'date' in c.lower() or 'month' in c.lower()]

    # Time series
    if date_cols and numeric_cols:
        return {
            "type": "line",
            "x": date_cols[0],
            "y": numeric_cols[0],
            "title": f"{numeric_cols[0]} over time"
        }

    # Category comparison
    if text_cols and numeric_cols and len(rows) <= 20:
        return {
            "type": "bar",
            "x": text_cols[0],
            "y": numeric_cols[0],
            "title": f"{numeric_cols[0]} by {text_cols[0]}"
        }

    # Distribution
    if len(numeric_cols) >= 1 and not text_cols:
        return {
            "type": "histogram",
            "x": numeric_cols[0],
            "title": f"Distribution of {numeric_cols[0]}"
        }

    return None

When SQL results are displayed, the system analyzes the column types and row count to suggest an appropriate visualization. For time-series data, it offers a line chart; for category comparisons, a bar chart; for distributions, a histogram. Users can toggle between table and chart views.

User Empowerment: Suggested questions and auto-charts remove friction. New users learn by example; power users can quickly visualize their data. The system feels helpful, not frustrating.

Deployment & Rollout

The Hybrid Query Intelligence layer is deployed as a new DeepAgent that integrates seamlessly with the existing orchestrator. Rollout follows these phases:

Phase 1: Internal Testing (Week 1-2)

  • Deploy Query Intelligence agent to staging
  • Internal team tests across all verticals (food, recruitment, retail, real estate)
  • Validate SQL generation, RAG retrieval, and synthesis
  • Collect observability data on failure patterns

Phase 2: Early Adopter Tenants (Week 3-4)

  • Enable feature flag for 3-5 pilot customers per vertical
  • Monitor query success rates, execution times, and user feedback
  • Gather telemetry on routing decisions and common questions
  • Iterate on SQL generation prompts based on failures

Phase 3: General Availability (Week 5+)

  • Enable for all tenants with feature flag defaults to ON
  • Maintain observability dashboard and feedback loop
  • Continuously improve based on query analytics
Success Metrics: Query success rate > 90%, average latency < 3s, user satisfaction > 4.5/5, hybrid route usage > 20% of queries. These metrics guide iteration and inform prioritization of improvements.
