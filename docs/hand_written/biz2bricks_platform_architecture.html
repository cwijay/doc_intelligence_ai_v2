Architectural Principles

  • Industry-Agnostic Core: The extraction, analysis, and reporting engines are generic. Industry-specific behavior is driven by configuration (document type schemas, workflows, dashboards) loaded from templates.
  • Template-Driven Configuration: Each industry has a pre-built template bundle (document types, extraction prompts, workflows, dashboard widgets). Tenants inherit these on signup and can customize via custom fields.
  • Schema-Extensible Design: Tenants can add custom fields to any document type without rebuilding the core system. The extraction pipeline merges base schema with custom fields at runtime.
  • Self-Service by Default: No manual onboarding. Tenants sign up, pick their industry, and start uploading. The system guides them with sample documents and pre-loaded workflows.
  • Multi-Tenant Isolation: Row-level security (RLS) in Cloud SQL, per-tenant GCS buckets, per-tenant Gemini File Search Stores. Complete data isolation.
  • AI-First Document Intelligence: Gemini 3 Flash is the workhorse for OCR, extraction, and initial analysis. File Search Store enables RAG for domain-specific Q&A. LangChain DeepAgents orchestrate multi-step workflows.

Section 2: Domain Abstraction Model

Why This Section Matters: This is the core innovation that makes Biz2Bricks truly generic. Instead of building separate code paths for Food, Recruitment, Retail, and Real Estate, we define a configuration-driven abstraction layer. All industries use the same extraction and analysis code; only the schemas and prompts differ.

Document Type Registry

Every document type (invoice, CV, PO, listing, etc.) is a configuration object, not hard-coded logic. This allows the system to scale to infinite document types without code changes.

# Core document type definition — works for ALL industries
@dataclass
class DocumentTypeDefinition:
    type_id: str                    # e.g., "invoice", "cv", "listing", "po"
    display_name: str               # e.g., "Invoice", "CV/Resume", "Job Listing"
    industry_id: str                # e.g., "food", "recruitment", "retail", "real_estate"
    base_schema: dict               # JSON Schema for core extractable fields
    custom_fields: list[CustomField] # Tenant-added fields
    extraction_prompt: str          # Gemini prompt template for this doc type
    validation_rules: list[Rule]    # Business rules (e.g., total = sum of items)
    icon: str                       # UI icon identifier
    tags: list[str]                 # Searchable tags, e.g., ["compliance", "qa"]

Extraction Schema System

The extraction schema is a JSON Schema that defines the structure Gemini will produce. The same extraction engine works for all document types — only the schema changes.

Custom Field Extension

Tenants can add fields without touching the core schema. A retail business might add "supplier_code", a food manufacturer might add "lot_number":

class CustomField:
    field_name: str        # e.g., "lot_number", "visa_status", "supplier_code"
    field_type: str        # "string", "number", "date", "enum", "boolean"
    enum_values: list[str] # For enum types: ["approved", "rejected", "pending"]
    required: bool
    extraction_hint: str   # Helps Gemini, e.g., "Look for batch number in top-left"

PostgreSQL Schema for Document Type Registry

This schema enables the entire configuration-driven abstraction:

CREATE TABLE document_types (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID NOT NULL REFERENCES tenants(id),
    industry_id TEXT NOT NULL,
    type_key TEXT NOT NULL,          -- 'invoice', 'cv', 'listing', 'po', etc.
    display_name TEXT NOT NULL,
    base_schema JSONB NOT NULL,      -- Full JSON Schema
    extraction_prompt TEXT NOT NULL,
    validation_rules JSONB DEFAULT '[]',
    icon TEXT DEFAULT 'file',
    is_system BOOLEAN DEFAULT false, -- true = from template, false = tenant-created
    created_at TIMESTAMPTZ DEFAULT now(),
    UNIQUE(tenant_id, type_key)
);

CREATE TABLE custom_fields (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    document_type_id UUID NOT NULL REFERENCES document_types(id) ON DELETE CASCADE,
    field_name TEXT NOT NULL,
    field_type TEXT NOT NULL CHECK (field_type IN ('string', 'number', 'date', 'enum', 'boolean')),
    enum_values JSONB,
    required BOOLEAN DEFAULT false,
    extraction_hint TEXT,
    sort_order INT DEFAULT 0,
    UNIQUE(document_type_id, field_name)
);

Section 4: Generic Agent Architecture (DeepAgents)

Core Principle: The agent system is industry-agnostic at its core. Every agent is generic. Industry-specific behavior comes from configuration (schemas, prompts, workflows) loaded at runtime. This is how we avoid code duplication across verticals.

Agent Types

Five specialist agents work together to deliver end-to-end document intelligence:

1. Document Ingestion Agent

Handles upload, file type detection, OCR via Gemini 3 Flash, structured extraction using document type schema, validation against business rules, and storage.

2. Analysis Agent

Performs pattern detection, trend analysis, anomaly detection, and insight generation. Works with configurable workflows specific to the document type.

3. Report Generation Agent

Creates formatted analysis reports, exports to PDF/XLSX, applies branding, and schedules recurring reports based on report templates.

4. Knowledge Agent

RAG-powered Q&A using Gemini File Search Store. Tenants ask questions about their documents; agent searches tenant's knowledge base and synthesizes answers.

Configurable Agent Factory

Instead of hardcoding agent behavior, we use a factory that assembles agents based on tenant's industry template and custom configuration. This enables multi-tenancy and extensibility:

from langchain_deepagents import create_deep_agent, SubAgentMiddleware

def create_tenant_orchestrator(tenant_id: str, industry_id: str):
    """Factory that builds a tenant-specific orchestrator based on their industry template."""
    template = load_industry_template(industry_id)
    custom_fields = load_custom_fields(tenant_id)

    # Build extraction tools dynamically from document type schemas
    extraction_tools = []
    for doc_type in template.document_types:
        schema = merge_schema(
            doc_type.base_schema,
            custom_fields.get(doc_type.type_key, [])
        )
        extraction_tools.append(
            build_extraction_tool(
                doc_type=doc_type,
                schema=schema,
                prompt_template=doc_type.extraction_prompt,
            )
        )

    # Build analysis tools from workflow definitions
    analysis_tools = [
        build_analysis_tool(workflow)
        for workflow in template.workflow_definitions
    ]

    # Generic agents that work across all industries
    ingestion_agent = create_deep_agent(
        model="gemini-3-flash",
        name=f"ingestion_{tenant_id}",
        tools=extraction_tools + [store_document, classify_document],
        instructions=INGESTION_SYSTEM_PROMPT.format(industry=industry_id),
    )

    analysis_agent = create_deep_agent(
        model="gemini-3-flash",
        name=f"analysis_{tenant_id}",
        tools=analysis_tools + [query_documents, generate_chart],
        instructions=ANALYSIS_SYSTEM_PROMPT.format(industry=industry_id),
    )

    knowledge_agent = create_deep_agent(
        model="gemini-3-flash",
        name=f"knowledge_{tenant_id}",
        tools=[rag_query, semantic_search],
        instructions=KNOWLEDGE_SYSTEM_PROMPT,
    )

    report_agent = create_deep_agent(
        model="gemini-3-flash",
        name=f"report_{tenant_id}",
        tools=[build_report, export_pdf, export_xlsx],
        instructions=REPORT_SYSTEM_PROMPT,
    )

    # Orchestrator delegates to specialist agents
    orchestrator = create_deep_agent(
        model="gemini-3-flash",
        name=f"orchestrator_{tenant_id}",
        tools=[],  # Uses SubAgentMiddleware for delegation
        middleware=[
            SubAgentMiddleware(agents={
                "ingestion": ingestion_agent,
                "analysis": analysis_agent,
                "knowledge": knowledge_agent,
                "report": report_agent,
            }),
            TenantContextMiddleware(tenant_id=tenant_id),
        ],
        instructions=ORCHESTRATOR_PROMPT.format(
            industry=template.display_name,
            doc_types=", ".join(dt.display_name for dt in template.document_types),
        ),
    )

    return orchestrator

Generic Extraction Tool

This tool works for ANY document type. It takes the document type's schema and extraction prompt, calls Gemini 3 Flash with JSON schema validation, and returns structured data:

from google import genai
from google.genai import types

def build_extraction_tool(
    doc_type: DocumentTypeDefinition,
    schema: dict,
    prompt_template: str
):
    """Build a Gemini-powered extraction tool for any document type."""

    client = genai.Client(vertexai=True, project="biz2bricks-prod", location="us-central1")

    async def extract(file_bytes: bytes, mime_type: str) -> dict:
        prompt = prompt_template.format(
            doc_type=doc_type.display_name,
            field_descriptions=schema_to_field_descriptions(schema),
        )

        response = await client.aio.models.generate_content(
            model="gemini-3-flash",
            contents=[
                types.Part.from_bytes(data=file_bytes, mime_type=mime_type),
                types.Part.from_text(text=prompt),
            ],
            config=types.GenerateContentConfig(
                response_mime_type="application/json",
                response_json_schema=schema,
                thinking_config=types.ThinkingConfig(thinking_level="medium"),
            ),
        )

        extracted = json.loads(response.text)

        # Run validation rules
        errors = validate_extraction(extracted, doc_type.validation_rules)

        return {
            "data": extracted,
            "errors": errors,
            "confidence": response.usage_metadata
        }

    extract.__name__ = f"extract_{doc_type.type_key}"
    extract.__doc__ = f"Extract structured data from {doc_type.display_name} documents"
    return extract

Section 5: Gemini File Search Store — Multi-Tenant RAG

Purpose: Each tenant gets their own Gemini File Search Stores for semantic search and RAG-powered Q&A over their documents. Complete isolation — Tenant A's queries never see Tenant B's data.

Per-Tenant Store Provisioning

When a tenant signs up, we create separate File Search Stores for each document category (e.g., "orders", "qc_records", "invoices"). This enables efficient scoped queries:

from google import genai
from google.genai import types

client = genai.Client(vertexai=True, project="biz2bricks-prod", location="us-central1")

async def provision_tenant_rag(tenant_id: str, industry_id: str):
    """Create File Search Stores for a new tenant — one per document category."""
    template = load_industry_template(industry_id)
    stores = {}

    # Group document types into logical categories for RAG
    categories = group_doc_types_by_category(template.document_types)

    for category_name, doc_types in categories.items():
        store = await client.aio.file_search_stores.create(
            config=types.CreateFileSearchStoreConfig(
                display_name=f"tenant-{tenant_id}-{category_name}",
                description=f"{category_name} documents for tenant {tenant_id}",
            )
        )
        stores[category_name] = store.name

    # Save store references to database
    await save_tenant_stores(tenant_id, stores)
    return stores

Ingestion Pipeline into RAG

After extraction, documents are indexed in the appropriate File Search Store. The Knowledge Agent can then query them:

async def ingest_to_rag(tenant_id: str, category: str, file_path: str):
    """Upload a processed document to the tenant's RAG store."""
    stores = await get_tenant_stores(tenant_id)
    store_name = stores[category]

    await client.aio.file_search_stores.upload(
        store_name=store_name,
        file_path=file_path,
    )

async def query_tenant_knowledge(
    tenant_id: str,
    question: str,
    categories: list[str] = None
) -> dict:
    """Query tenant's knowledge base using Gemini File Search."""
    stores = await get_tenant_stores(tenant_id)

    # Select relevant stores (defaults to all if not specified)
    store_names = [stores[c] for c in (categories or stores.keys())]

    response = await client.aio.models.generate_content(
        model="gemini-3-flash",
        contents=question,
        config=types.GenerateContentConfig(
            tools=[
                types.Tool(file_search=types.FileSearch(
                    file_search_store_names=store_names
                ))
            ],
        ),
    )

    return {
        "answer": response.text,
        "sources": [
            {"file": chunk.file_name, "snippet": chunk.text}
            for chunk in response.candidates[0].grounding_metadata.chunks
        ],
    }

RAG Scaling Considerations

  • Store Size Management: For high-volume tenants, consider splitting categories further (e.g., "orders_2024_q1", "orders_2024_q2") to keep individual stores performant.
  • Document Freshness: When a document is updated or deleted, remove from RAG store and re-ingest. Track document versions.
  • Query Cost Optimization: Use category filtering to limit which stores are queried; don't always search all stores.
  • Data Privacy: File Search Stores are fully isolated per tenant. No possibility of cross-tenant leakage in RAG results.
  • Bulk Operations: For bulk document imports, batch ingestion to RAG (e.g., ingest 100 documents per job to avoid timeouts).
Cost Efficiency Tip: Store only the processed/formatted document in RAG (e.g., a cleaned PDF with extracted data highlighted). Don't store raw scans or intermediate files. This reduces storage costs and improves search quality.

export function AIChat() {
  const [messages, setMessages] = useState<Message[]>([])
  const [streaming, setStreaming] = useState(false)

  const sendMessage = async (input: string) => {
    const userMsg = { role: 'user', content: input }
    setMessages(prev => [...prev, userMsg])
    setStreaming(true)

    const response = await fetch('/api/chat', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ message: input }),
    })

    const reader = response.body!.getReader()
    const decoder = new TextDecoder()
    let assistantMsg = { role: 'assistant', content: '', sources: [] }

    while (true) {
      const { done, value } = await reader.read()
      if (done) break

      const chunk = decoder.decode(value)
      const lines = chunk.split('\n').filter(l => l.startsWith('data: '))

      for (const line of lines) {
        const data = JSON.parse(line.slice(6))
        if (data.type === 'text') {
          assistantMsg.content += data.content
        }
        setMessages(prev => [...prev.slice(0, -1), assistantMsg])
      }
    }

    setStreaming(false)
  }

  return /* Chat UI with message bubbles and sources */
}

Tenant Context Injection via Middleware

Every request is enriched with tenant context via middleware, ensuring all downstream services know which tenant is making the request:

// middleware.ts
import { NextResponse } from 'next/server'
import { getToken } from 'next-auth/jwt'
import type { NextRequest } from 'next/server'

export async function middleware(request: NextRequest) {
  const token = await getToken({ req: request })

  if (!token?.tenant_id) {
    return NextResponse.redirect(new URL('/login', request.url))
  }

  // Inject tenant context into headers for all downstream services
  const headers = new Headers(request.headers)
  headers.set('x-tenant-id', token.tenant_id)
  headers.set('x-tenant-industry', token.industry_id)
  headers.set('x-user-role', token.role)

  return NextResponse.next({ headers })
}

async def get_tenant_schema_description(tenant_id: str) -> str:
    """Build natural language schema description for SQL generator."""

    doc_types = await db.fetch_all("""
        SELECT dt.type_key, dt.display_name, dt.base_schema,
               json_agg(json_build_object(
                   'name', cf.field_name,
                   'type', cf.field_type,
                   'hint', cf.extraction_hint
               )) FILTER (WHERE cf.id IS NOT NULL) AS custom_fields
        FROM document_types dt
        LEFT JOIN custom_fields cf ON cf.document_type_id = dt.id
        WHERE dt.tenant_id = :tenant_id
        GROUP BY dt.id
    """, {"tenant_id": tenant_id})

    lines = ["## Database Schema", ""]
    lines.append("### Core Tables")
    lines.append("- `documents` (id, tenant_id, document_type_id, gcs_path, status, created_at)")
    lines.append("- `extracted_data` (id, document_id, tenant_id, data JSONB, validation_errors, extracted_at)")
    lines.append("")

    for dt in doc_types:
        lines.append(f"### Document Type: {dt['display_name']} (type_key='{dt['type_key']}')")

        schema = dt['base_schema']
        if 'properties' in schema:
            lines.append("Base fields in `extracted_data.data`:")
            for field_name, field_def in schema['properties'].items():
                field_type = field_def.get('type', 'string')
                lines.append(f"  - `data->>'{field_name}'` ({field_type})")

        if dt['custom_fields']:
            lines.append("Custom fields (tenant-added):")
            for cf in dt['custom_fields']:
                hint = cf['hint'] or 'no hint'
                lines.append(f"  - `data->>'{cf['name']}'` ({cf['type']}) — {hint}")

        lines.append("")

    return "\n".join(lines)

SQL Validation & Sanitization

Before execution, SQL is validated using sqlglot to prevent injection and ensure only safe SELECT statements run:

import sqlglot

def validate_sql(sql: str, tenant_id: str) -> str:
    """Validate and sanitize generated SQL before execution."""

    # 1. Parse with sqlglot to ensure valid SQL
    try:
        parsed = sqlglot.parse_one(sql, dialect="postgres")
    except sqlglot.errors.ParseError as e:
        raise SQLValidationError(f"Invalid SQL syntax: {e}")

    # 2. Reject any non-SELECT statements
    if not isinstance(parsed, sqlglot.exp.Select):
        raise SQLValidationError("Only SELECT statements are allowed")

    # 3. Check for dangerous operations
    dangerous_ops = (
        sqlglot.exp.Delete, sqlglot.exp.Update, sqlglot.exp.Insert,
        sqlglot.exp.Drop, sqlglot.exp.Alter, sqlglot.exp.Create,
    )
    for node in parsed.walk():
        if isinstance(node, dangerous_ops):
            raise SQLValidationError(f"Forbidden operation: {type(node).__name__}")

    # 4. Ensure tenant_id filter exists
    if "tenant_id" not in sql.lower():
        raise SQLValidationError("Query must include tenant_id filter")

    # 5. Add LIMIT if not present
    if not parsed.find(sqlglot.exp.Limit):
        sql = f"SELECT * FROM ({sql}) _limited LIMIT 100"

    return sql
Safety Guardrails: All SQL queries have a 5-second execution timeout and 100-row limit (unless aggregating). This prevents runaway queries from consuming resources. Parameterized tenant_id ensures no string interpolation. RLS at the database level provides defense-in-depth.

async def safe_execute_sql(sql: str, tenant_id: str, timeout_ms: int = 5000) -> dict:
    try:
        # Validate SQL
        validated_sql = validate_sql(sql, tenant_id)

        # Execute with timeout
        async with db.connection() as conn:
            await conn.execute("SET app.current_tenant = :tid", {"tid": tenant_id})
            await conn.execute(f"SET statement_timeout = {timeout_ms}")

            start = time.monotonic()
            rows = await conn.fetch_all(validated_sql, {"tenant_id": tenant_id})
            execution_time = time.monotonic() - start

            await log_query_execution(tenant_id=tenant_id, sql=validated_sql, execution_time_ms=execution_time * 1000, status="success")

            return {
                "rows": [dict(r) for r in rows],
                "sql": validated_sql,
                "execution_time_ms": execution_time * 1000
            }

    except asyncio.TimeoutError:
        await log_query_execution(tenant_id=tenant_id, sql=sql, status="timeout")
        return {"error": "Query took too long. Try a more specific question.", "sql": sql}

    except Exception as e:
        await log_query_execution(tenant_id=tenant_id, sql=sql, status="error", error=str(e))
        return {"error": "Query execution failed. Falling back to document search.", "sql": sql}

async def cached_sql_execute(sql: str, tenant_id: str, cache_ttl: int = 300) -> dict:
    """Cache SQL results in Redis for 5 minutes."""
    cache_key = f"sql:{tenant_id}:{hashlib.sha256(sql.encode()).hexdigest()}"

    # Check cache first
    cached = await redis.get(cache_key)
    if cached:
        return json.loads(cached)

    # Execute if not cached
    result = await safe_execute_sql(sql, tenant_id)

    # Cache successful results
    if "error" not in result:
        await redis.setex(cache_key, cache_ttl, json.dumps(result, default=str))

    return result
